# DECISIONS — принятые решения

Формат: решение → причина → следствия. Если меняете решение, добавьте новую
запись с датой, не переписывайте старую молча.

## D1. Один глобальный активный вид спорта (устарело, см. D20)

**Решение:** `settings.active_sport` — единственный активный вид. Движок
опрашивает линию только его.

**Причина:** телефон и лимит API Betcity не тянут шесть видов одновременно;
пользователю нужен предсказуемый фокус и понятная статистика.

**Следствия:** правила/шаблоны/метрики хранятся по видам; переключение вида
обновляет очередь, результаты, статистику, конструктор и анализатор; нельзя
держать «фоновый» другой вид.

## D2. ID видов Betcity

**Решение:** футбол `1`, теннис `2`, баскетбол `3`, хоккей `7`, волейбол
`12`, настольный теннис `46`.

**Причина:** live endpoint единый, вид выбирается ключом в
`reply.sports`.

**Следствия:** если Betcity изменит ID, правится только `sports.py`;
`normalize_sport` должен понимать алиасы (`tt`, `football`, «футбол» и т.п.).

## D3. Единый live endpoint

**Решение:** `https://d.betcity.by/api/v1/live/bets` для всех видов.

**Причина:** проверено на шести видах; отдельные API не нужны.

**Следствия:** парсер один; вид определяется по спортивному ключу. Ошибки
разметки ловятся фикстурами.

## D4. Нормализация статистики командных видов

**Решение:** статистика командных видов приводится к форме записей
настольного тенниса (`match_score`, `sets`, `match_total`, `winner`,
`btts`).

**Причина:** переиспользовать 75 метрик и шаблоны TT без второй системы
метрик.

**Следствия:** `record_from_score` — критичная функция; парсер TT не
трогаем; новые виды обязаны пройти `test_sports_pipeline.py`.

## D5. Разные рынки для разных видов

**Решение:**

- TT: `winner`, `total` (по партиям);
- футбол/хоккей: `winner` (+`x`), `total`, `handicap`, `btts` (по матчу);
- баскетбол/волейбол/теннис: `winner`, `total`, `handicap` (по матчу).

**Причина:** соответствие реальным рынкам Betcity и смыслу вида.

**Следствия:** UI и `_clean_rule` обязаны фильтровать рынки по виду; нельзя
дать `btts` баскетболу.

## D6. Generic-алгоритм для командных видов

**Решение:** встроенный режим для командных видов и тенниса — прозрачная
эвристика: форма за 5 игр + H2H до 10 + линия тотала, порог `margin` по
виду.

**Причина:** полноценная модель TT не переносится на футбол; пользователю
нужен понятный baseline, а точные рынки — через конструктор.

**Следствия:** generic не обещает высокой точности; его прогнозы ограничены
уверенностью 0.82; тонкие рынки — только конструктор.

## D7. Конструктор как основной инструмент

**Решение:** пользовательские правила с метриками, группами И/ИЛИ и
действиями; шаблоны — стартовая точка.

**Причина:** пользователь хочет управлять логикой и понимать, почему прогноз
сработал.

**Следствия:** каждое правило описывается текстом; анализатор переносит
условия; шаблоны не гарантируют прибыль.

## D8. Отдельные файлы правил по видам

**Решение:** `constructor_rules.json` для TT,
`constructor_rules_<sport>.json` для остальных.

**Причина:** смена вида не должна затирать правила; формат — читаемый JSON.

**Следствия:** при добавлении вида нужно завести файл; `_path_for` —
единственное место формирования пути.

## D9. Фора хранится со знаком стороны

**Решение:** Ф1 — отрицательное значение, Ф2 — положительное; push даёт
`success = null`.

**Причина:** однозначный расчёт без догадок о стороне.

**Следствия:** UI и импорт не должны нормализовать знак; push не портит
hit rate.

## D10. Ограничение порогов

**Решение:** тотал 0..100 для TT, 0..1000 для остальных.

**Причина:** защита от опечаток (например, тотал `99999` для футбола).

**Следствия:** при новых видах с большими тоталами поднять лимит осознанно.

## D11. Ручной перенос и авто-режим разделены

**Решение:** обычный перенос условия открывает редактор и не сохраняет правило
без подтверждения. Отдельный авто-режим (`auto_rules.py`) сам создаёт правила,
но помечает их `auto: true` и не трогает ручные.

**Причина:** корреляция ≠ причинность; при этом пользователь хочет непрерывную
доработку без ручного копирования каждого условия.

**Следствия:** кнопка «В конструктор» по-прежнему открывает модалку; для неудач
оператор инвертируется. Авто-правила требуют минимальной выборки, точности и
доминирования одного действия.

## D12. Bridge Kotlin ↔ JS синхронный

**Решение:** `@JavascriptInterface` вызывает Python и сразу возвращает
JSON-строку.

**Причина:** простота Chaquopy и отсутствие async-инфраструктуры в WebView.

**Следствия:** нельзя делать тяжёлые вызовы в цикле; сеть только по явному
действию или в фоне движка; ошибки возвращаются как `{"ok": false}`.

## D13. Fallback-вызовы predictor-методов

**Решение:** вызовы с новыми аргументами оборачиваются в `try/except
TypeError` с откатом к старой сигнатуре.

**Причина:** тесты и внешние monkeypatch могут подменять методы.

**Следствия:** при изменении сигнатур сохраняйте fallback; не удаляйте
`try/except TypeError` без проверки тестов.

## D14. Без git

**Решение:** резервные копии в `.backups/<дата>_<тема>/`.

**Причина:** проект исторически без репозитория; пользователю нужны простые
восстановимые копии.

**Следствия:** перед крупными правками копируйте исходники; не полагайтесь
на историю редактора.

## D15. WebView + статические assets

**Решение:** интерфейс — `index.html` + `app.js` + `style.css` без
фреймворка и сборщика.

**Причина:** офлайн-работа, отсутствие npm, простой деплой в APK.

**Следствия:** весь JS в одном файле; вставляйте данные через `esc()`;
периодические обновления ограничены.

## D16. Вендоринг Python-пакетов

**Решение:** `requests`, `bs4` и зависимости лежат в
`app/src/main/python/`; pip не используется.

**Причина:** Chaquopy собирает `app.imy` из дерева исходников; нет
requirements-шага.

**Следствия:** новый пакет нужно копировать целиком; следите за лицензиями и
размером APK.

## D17. Debug-подпись для личной сборки

**Решение:** сейчас APK подписывается debug-ключом.

**Причина:** приложение ставится вручную, публикация не планируется.

**Следствия:** для распространения нужен release keystore и отдельная
процедура.

## D18. Настольный теннис не переписывается

**Решение:** парсер и модели TT сохраняются как есть; новые виды
адаптируются вокруг них.

**Причина:** TT — рабочая проверенная база на 46 шаблонов и 542 проверки.

**Следствия:** любые изменения TT требуют полного прогона TT-регрессий.

## D19. Авто-правила только с метаданными

**Решение:** авто-правило обязано иметь `auto: true`, `auto_key`,
`auto_kind`, `auto_target` и `auto_stats`; `_clean_rule` сохраняет эти поля.

**Причина:** без метаданных после `save()` правило нельзя отличить от ручного,
перепроверить на новой истории или показать точность.

**Следствия:** ручное редактирование авто-правила в UI снимает `auto` и
превращает его в обычное; генератор его больше не заменяет. При добавлении
новых полей правила обновляйте `_clean_rule` и `tests/test_auto_rules.py`.

## D20. Движок анализирует все виды сразу

**Решение:** `get_live_matches()` без аргумента возвращает матчи всех шести
видов из одного ответа Betcity. `run_cycle()` обрабатывает все матчи, а
`refresh_queue()` показывает все виды. `active_sport` остаётся только выбором
интерфейса: какие правила, шаблоны и метрики показывать. Явный
`get_live_matches("football")` используется для точечного теста правил.

**Причина:** пользователю нужны прогнозы по всем настроенным видам без ручного
переключения; один общий live-фид уже содержит все виды, поэтому шесть
отдельных запросов не нужны.

**Следствия:** авто-правила пересобираются отдельно для каждого вида, а
включение/выключение авто действует на все виды. Очередь и главная панель
показывают общее число матчей и метку вида у каждого матча. Правила видов
по-прежнему хранятся раздельно: вид без правил в режиме конструктора просто не
даёт прогнозов. Регрессия — `tests/test_all_sports.py`.

## D21. Нейросеть учится на всех проверенных матчах

**Решение:** встроенный многослойный персептрон (`nn_core.py` + `nn_trainer.py`)
обучается на примерах **каждого** проверенного матча — с прогнозом и без него.
Признаки берутся из метрик конструктора, метки — из финального счёта Betcity.
Модель своя для каждого вида спорта, обучение идёт в фоне и продолжает
дообучение, а не начинается заново. Прогнозы сети выдаются только при
включённом переключателе `neural.enabled`.

**Причина:** пользователю нужен алгоритм, который учится на собственной
истории, и прозрачный показатель «насколько он обучен». Данных с прогнозами
мало, а проверенных матчей в разы больше — на них и держится обучение.

**Следствия:** в цикле признаки считаются один раз и используются и для
обучения, и для прогноза. Разметку завершённых матчей делает поток проверки
результатов, поэтому сеть учится даже при остановленном движке. Правила
конструктора приоритетнее сети: при совпадении рынка выигрывает правило.
Файлы `nn_samples.jsonl`, `nn_pending.json`, `nn_model.json` живут в
`predictor_data`. Регрессия — `tests/test_nn.py`.

## D22. Защита сети от переобучения

**Решение:** постоянное самообучение сети идёт под четырьмя защитами:
`neural.keep_best` (новая модель принимается, только если её точность на
отложенной выборке не хуже прежней — иначе остаётся прежняя и пишется в лог
«переобучение отклонено»), `neural.freeze` (веса не меняются автоматически),
остановка по плато (3 раунда без роста точности) и резервная копия модели с
откатом одной кнопкой. В карточке показывается история обучения, тренд и
признак плато.

**Причина:** сеть обучается на continuously растущей выборке, поэтому со
временем она начинает запоминать обучающие примеры вместо обобщения. Ранняя
версия заменяла модель безусловно, и деградация была видна только по
упавшей цифре — без возможности вернуть хорошую модель.

**Следствия:** «хорошая модель» — это не максимум accuracy, а её **lift** над
базой («всегда самый частый исход») на отложенной выборке; при lift ≤ 0 вид
отключают чипом. Откат меняет модель местами с резервной копией, поэтому
после отката предыдущая модель становится резервной (откат можно повторять).
Плато останавливает только автоматическое дообучение — ручная кнопка
«Обучить сейчас» работает всегда. Регрессия — `tests/test_nn.py`.

## D23. AI-ассистент не влияет на расчёт ставок

**Решение:** облачная языковая модель (Gemini по умолчанию, поддерживаются
DeepSeek, Groq, OpenRouter и любой OpenAI-совместимый endpoint) подключается
опционально и решает только текстовые задачи: объяснить прогноз, собрать
черновик правила из анализа, подвести итоги, проверить правила. Мнение модели
по матчу сохраняется как отдельный источник «ИИ» — оно не участвует в
расчёте ставки, но проверяется по финальному счёту, чтобы его можно было
честно сравнить с правилами.

**Причина:** языковая модель не видит линию в реальном времени и не учится на
истории пользователя, поэтому её «прогноз» — это мнение, а не статистически
проверенный сигнал. Смешивать его со ставками значит рисковать без
возможности измерить эффект. Объяснять и подсказывать модель умеет отлично.

**Следствия:** запросы идут только по явной кнопке, ответы кэшируются
(`ai_cache.json`), действует дневной лимит и лимит на цикл движка, ключ хранится
только на устройстве. Без ключа или без сети приложение работает как обычно.
Все провайдеры используют один OpenAI-совместимый код. Регрессия —
`tests/test_ai.py`.

## D24. ИИ выбирает виды и рынки, мнение можно встроить

**Решение:** пользователь отмечает виды спорта и отдельные рынки для ИИ
(`ai.sports`, `ai.markets`). Если вид не отмечен, `markets_for()` возвращает
пустой список и модель не вызывается. Переключатель `ai.embed` включает
встраивание: ИИ вызывается только при наличии прогноза правил или сети, а его
мнение добавляется в то же сообщение и помечается `embedded`. Если прогноза
нет, запрос не выполняется. `ai.auto_predict` по-прежнему разрешает отдельные
ИИ-сообщения, когда встраивание выключено.

**Причина:** пользователю нужны не все шесть видов сразу, а именно те, где он
собирает статистику. Встраивание убирает поток отдельных сообщений «только
мнение ИИ», которые не участвуют в ставке, но тратят лимит.

**Следствия:** лимит `per_cycle` общий для обоих режимов; счётчик тратится
перед запросом, чтобы сбой модели не съедал лимит за один цикл. В истории
мнение остаётся отдельным источником `ai` и проверяется по счёту. Регрессия —
`tests/test_ai.py`.

## D25. Проверка действующих правил отдельно от авто-генерации

**Решение:** `auto_rules.review_rules()` проверяет включённые правила и
возвращает вердикт и готовый `patch`, а `Engine.get_analyzer` добавляет блок
`rule_reviews` в ответ анализа. Проверка не зависит от `auto_rules.enabled`:
она ничего не создаёт и не удаляет, только предлагает правку. Применение
идёт через существующие `constructor` + `saveConstructor`; перед сохранением
правила вида читаются заново.

**Причина:** авто-генерация отвечает за новые правила, но не за качество уже
работающих. Пользователю нужен ответ «что делать с текущими правилами», а не
только «вот ещё несколько».

**Следствия:** ужесточение разрешено только для логики «И» — добавление
условия в «ИЛИ» расширило бы правило. При малой выборке возвращается
`collect`, а не правка. Отключение обратимо: правило остаётся в конструкторе.
Регрессия — `tests/test_auto_rules.py` (включая ответ API анализа).

## D26. Разметка нейросети не зависит от новых матчей

**Решение:** `_nn_maintenance()` вызывается в цикле сразу после получения
линии и до раннего выхода «нет матчей». Ожидание финала увеличено с 36 до
72 часов. В обратном распространении для tanh используется активация
скрытого слоя (`acts[layer_index]`), а не входа.

**Причина:** при пустой линии цикл выходил раньше разметки, поэтому примеры
копились, а модель не обновлялась. Ошибка производной не давала сети осваивать
нелинейные признаки — точность упиралась в базовый уровень.

**Следствия:** `ResultChecker` по-прежнему размечает при остановленном
движке; цикл движка страхует этот путь. Диагностика `nn_trainer.status()`
объясняет по каждому виду, чего не хватает. Регрессия — `tests/test_nn.py`
(включая XOR на скрытом слое).
