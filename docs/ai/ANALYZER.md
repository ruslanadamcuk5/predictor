# ANALYZER — анализатор истории

## 1. Задача

Анализатор отвечает на вопрос: **какие условия в момент прогноза чаще
сопровождали успех или неудачу**. Он не предсказывает матчи. Результат — список
условий, связок и средних значений, которые пользователь может перенести в
конструктор вручную или включить авто-формирование (`auto_rules.py`).

Анализатор работает только по прогнозам, у которых:

1. есть сохранённый снимок статистики (`stats` с `kind: "context"`);
2. есть проверенный результат (`success = true/false`).

Прогнозы без снимка или без результата в выборку не попадают.

## 2. Снимок контекста

При отправке прогноза `analyzer.make_sample(match, stats)` сохраняет:

```json
{
  "kind": "context",
  "sport": "football",
  "match": {
    "team1": "...",
    "team2": "...",
    "league": "...",
    "date": "...",
    "score": "...",
    "odds": {}
  },
  "page_total": {"line": 2.5, "over": 1.9, "under": 1.9},
  "recent": {"p1": [...], "p2": [...]},
  "h2h": [...]
}
```

`context_from_sample` восстанавливает объект `Context` из
`constructor_engine`. Поэтому анализатор переиспользует те же метрики и
операторы, что и конструктор. Если формат снимка меняется, нужно обновить
`make_sample` и `context_from_sample` одновременно.

`json_safe` / `json_restore`:

- даты переводятся в строки;
- кортежи — в списки;
- `NaN`/`Infinity` — в `null`;
- служебный маркер `__dt__` позволяет восстановить datetime.

Не кладите в снимок объекты, которые нельзя сериализовать в JSON.

## 3. Наблюдение

Для каждого прогноза с результатом создаётся наблюдение:

| Поле | Смысл |
|---|---|
| `id` | id отправленного прогноза |
| `ctx` | восстановленный контекст |
| `sport` | вид спорта |
| `success` | true/false |
| `kind` | `total`, `winner`, `handicap`, `btts` |
| `target` | `match`, `set1`..`set5` |
| `verdict`, `label` | текст прогноза |
| `team1`, `team2`, `league` | матч |
| `sent_at` | когда отправлен |
| `score`, `total` | результат |
| `prediction` | полный прогноз (рынок, цель, `expected_side`, линия) — нужен авто-генератору, чтобы восстановить действие правила |

Фильтры `build_observations`:

- `kind` — рынок;
- `target` — конкретная партия/матч;
- `sport` — вид спорта;
- `limit` — последние N наблюдений (сортировка по `sent_at` по убыванию).

## 4. Кандидаты

`candidate_variants(sport)` перебирает метрики выбранного вида и порождает
варианты аргументов:

- `side` — `p1` и `p2`;
- `window` — значение по умолчанию и `3`, если окно больше 3;
- `set` — 1 и 2;
- строковые метрики пропускаются.

Для числовых метрик пороги строятся по квантилям/границам распределения
(`_numeric_candidates`), для enum/string — по встречающимся значениям. Пороги
округлены «красиво» (`_nice_threshold`).

## 5. Оценка условий

Для каждого варианта и оператора считается:

- `win_hits` / `loss_hits` — сколько успешных/неуспешных наблюдений
  удовлетворяют условию;
- `win_share` / `loss_share` — доля внутри своей группы;
- `coverage` — какая часть всех наблюдений покрыта;
- `lift` — разница долей;
- `score` — комбинированная оценка для сортировки.

Базовые константы:

| Константа | Значение | Смысл |
|---|---:|---|
| `MIN_GROUP` | 3 | минимум успехов и неудач для выводов |
| `MIN_HITS` | 2 | минимум попаданий условия |
| `MIN_LIFT` | 10.0 | минимальный перевес, п.п. |
| `MAX_ROWS` | 40 | максимум строк на раздел |
| `MAX_EXAMPLES` | 2 | примеров на строку |

`sufficient` в ответе — `wins >= min_group and losses >= min_group`. Если
данных мало, анализатор возвращает `hint` и пустые списки, но всё равно может
показать средние значения.

## 6. Что возвращается

```json
{
  "ok": true,
  "options": {"kind": "all", "target": "", "min_group": 3,
              "min_lift": 10, "min_hits": 2, "sport": "football"},
  "observations": {"total": 40, "wins": 22, "losses": 18, "with_stats": 55},
  "min_group": 3,
  "sufficient": true,
  "generated_at": "20.10.2026 10:00",
  "failure": [],
  "success": [],
  "combos": {"failure": [], "success": []},
  "means": [],
  "money": {"roi": 12.4, "ev": 12.4, "ev_lower": 4.1,
             "profit": 8.2, "avg_odds": 1.94, "odds_n": 36,
             "odds_covered": 90.0, "drawdown": 3.0, "stake_pct": 1.8},
  "portfolio": {"core": [], "watch": [], "rules": [],
                 "budget_pct": 10.0, "hint": "…"}
}
```

- `failure` — условия, чаще встречавшиеся при неудаче;
- `success` — условия, чаще встречавшиеся при успехе;
- `combos` — пары условий из топ-6, до 6 связок;
- `means` — до 15 числовых метрик с `win_mean`, `loss_mean`, `delta`,
  `normalized`.

Связка (`combo`) требует:

- минимум 2 попадания;
- долю не ниже 60%;
- перевес над противоположной группой не ниже 20 п.п.

## 7. Перенос в конструктор

Кнопка «В конструктор» вызывает `analyzerToConstructor(conditions, invert,
name, texts)` и открывает окно `attachModal`:

- превью условий и пометка, будет ли условие инвертировано;
- чипы вида спорта (по умолчанию — вид из фильтра анализатора);
- «＋ Создать новое правило»;
- список существующих правил выбранного вида с действием, числом условий,
  приоритетом и флагом «стоп»;
- для условий неудачи оператор инвертируется по таблице `AN_INVERSE`
  (`gt` ↔ `lt`, `gte` ↔ `lte`, `eq` ↔ `neq`, `in` ↔ `not_in` и т.п.) **до**
  показа окна и до сохранения;
- новое правило получает имя с префиксом «Как в удачах:» или
  «Не как в неудачах:»; при добавлении в существующее имя не меняется;
- условие добавляется в корневую группу «И» правила; дубликаты по
  `attachRuleKey` (метрика, аргументы, оператор, значение) пропускаются;
- если правило другого вида, `ensureSportThen` переключает активный вид;
- правило не сохраняется автоматически: открывается редактор с notice,
  пользователь проверяет и нажимает «Сохранить»; после сохранения карточка
  правила подсвечивается.

Перед показом списка `attachCompatibility` проверяет, что все метрики условия
есть в каталоге выбранного вида спорта; несовместимое условие блокируется
предупреждением.

Это важно: анализатор показывает корреляцию, а не причинность. Перенесённое
правило нужно проверить на свежих данных.

## 8. Авто-правила

`auto_rules.py` превращает находки анализатора в правила конструктора. Вход —
`telegram.sent_predictions`, выход — список правил с `auto: true`.

Алгоритм:

1. `analyzer.build_observations(..., sport=...)` и группировка по паре
   `(kind, target)`: `set1..set5` для настольного тенниса, `match` для
   командных видов.
2. Для каждой группы с достаточным числом удач и неудач запускается
   `analyzer.analyze(kind=..., target=..., with_pairs=False,
   with_means=False)`.
3. Кандидаты: одно условие из удач, одно инвертированное условие из неудач,
   две пары условий и смешанная пара. Операторы инвертируются по `INVERSE_OPS`;
   `between` и `value_metric` не инвертируются.
4. Кандидат проверяется на **всей** группе: `n`, точность, покрытие, средняя
   точность группы. Нужно `n >= min_samples`, точность не ниже
   `min_precision` и хотя бы на `MIN_IMPROVEMENT` (5 п.п.) выше базовой.
5. Действие берётся из зашедших прогнозов, попавших под условие: рынок,
   цель, сторона, линия тотала/форы. Действие должно доминировать
   (`MIN_ACTION_SHARE = 0.60`), иначе правило отбрасывается.
6. Дополнительно строится правило-пропуск, если условие даёт не менее 75%
   неудач и покрывает не более половины группы.
7. Старые авто-правила перепроверяются на новой истории; ослабшие удаляются.
   Ручные правила (`auto` отсутствует) не изменяются.

Метаданные авто-правила:

| Поле | Смысл |
|---|---|
| `auto` | признак автоматического правила |
| `auto_key` | стабильный ключ (hash действия и условий) |
| `auto_kind`, `auto_target` | рынок и цель для повторной проверки |
| `auto_source` | `success`, `failure` или `mixed` |
| `auto_stats` | `precision`, `coverage`, `matched`, `wins`, `losses`, `base_precision`, `updated_at` |

`constructor_engine._clean_rule` обязан сохранять эти поля — иначе после
`save()` авто-правило станет ручным и перестанет обновляться.

Настройки в `BotSettings.DEFAULTS["auto_rules"]`:

```json
{"enabled": false, "min_precision": 60.0, "min_samples": 6, "max_rules": 4}
```

Движок пересобирает правила не чаще `AUTO_RULES_INTERVAL = 180` секунд: в
`Engine._loop` после цикла и в `run_once`, плюс вручную через
`api_auto_rules`. Пересчёт идёт **по каждому виду отдельно**
(`_refresh_all_auto_rules()`), потому что движок анализирует все виды сразу.
Включение переключает `algorithm_mode` на `constructor`; выключение оставляет
ручные правила и выключает только авто-правила во всех видах. Если
данных меньше `min_samples`, уже накопленные авто-правила не удаляются.

## 8б. Проверка активных правил

`auto_rules.review_rules(sent_predictions, sport, rules, observations=None,
min_samples=6, min_precision=60.0)` проверяет **уже включённые** правила и
возвращает готовые правки. Вызывается из `Engine.get_analyzer`, поэтому
работает и при выключенной авто-генерации.

Порядок:

1. Для каждого правила берётся рынок и цель (`_rule_market`) и группа
   наблюдений `(kind, target)`.
2. Условия правила (`_rule_conditions`) отбирают совпавшие наблюдения
   (`_matched_group`); пустые условия — вся группа.
3. Считаются `matched`, `wins`, `losses`, точность правила и средняя
   точность рынка (`base_precision`). Для правила-пропуска точность — доля
   отсечённых неудач (`SKIP_LOSS_SHARE = 75.0`).
4. Вердикт:
   - `no_data` — по рынку нет проверенных прогнозов или условия не совпали;
   - `collect` — срабатываний меньше `min_samples`;
   - `disable` — точность ниже цели и ниже рынка, а безопасного усиления нет;
   - `tighten` — найдено обратное условие из неудач (`_tighten_rule`), которое
     поднимает точность минимум на 5 п.п.; для логики «ИЛИ» ужесточение
     запрещено, чтобы не расширить правило;
   - `loosen` — снятие одного условия из «И» даёт больше срабатываний без
     потери точности (`_loosen_rule`);
   - `confidence` — уверенность действия расходится с фактической точностью
     больше чем на 12 п.п.;
   - `keep` — правило устойчиво.
5. `patch` — готовый фрагмент правила: `{"enabled": false}`,
   `{"conditions": {...}}` или `{"action": {...}}`. JS применяет его через
   `constructor` + `saveConstructor`, заново читая правила вида.

Ответ: `{ok, sport, reviews, total, active, disabled, counts, hint,
updated_at}`. В каждом отзыве — `id`, `name`, `title`, `verdict`, `label`,
`suggestion`, `patch`, `precision`, `base_precision`, `lift`, `matched`,
`group_size`, `confidence`, `conditions_text`, `action_text`.

Для нескольких видов `analysis_service.build_report` вызывает
`review_rules` по каждому выбранному виду и объединяет отзывы, добавляя
`sport`, `sport_name`, `sport_short`. Верхние `sport` пуст, если видов
больше одного; полный список — `sports_selected`.

## 8в. Рекомендации по правилам (`rule_advisor.py`)

`analysis_service` после проверки правил вызывает
`rule_advisor.recommend(sent_predictions, sports, rules_by_sport,
observations_by_sport, min_samples, min_precision, state, active_sport)`.
Модуль не зависит от Android и файловой системы: состояние передаётся
словарём, сохраняет его вызывающая сторона.

Типы рекомендаций:

| Тип | Что предлагает | Patch |
|---|---|---|
| `add_condition` | добавить условие в конкретное правило | `{"conditions": {...}}` |
| `remove_condition` | убрать лишнее условие | `{"conditions": {...}}` |
| `disable_rule` | отключить правило | `{"enabled": false}` |
| `add_odds_floor` | поднять минимальный коэффициент | `{"conditions": {...}}` |
| `adjust_confidence` | исправить уверенность действия | `{"action": {...}}` |

Каждая рекомендация содержит `id`, `sport`, `rule_id`, `rule_name`,
`target_rule` (имя, действие, приоритет, текущие условия), `type`,
`type_title`, `severity`, `condition`, `condition_text`, `precision_before`,
`precision_after`, `matched_before`, `matched_after`, `removed_losses`,
`odds_before`, `roi_before`, `roi_after`, `ev_before`, `ev_after`,
`profit_after`, `reason`, `patch`, `is_new`.

Идентификатор стабилен: `sha1(sport | rule_id | type | condition_key)`.
Состояние (`advisor_state.json`) хранит `seen`, `applied`, `resolved`,
`dismissed`; `seen` даёт счётчик новых, `dismissed` скрывает совет на
`DISMISS_DAYS = 7` дней, `applied`/`resolved` закрывают его навсегда.

Перед выдачей каждая рекомендация проверяется через `_is_resolved` по
**актуальному** правилу. Поэтому условие, добавленное вручную в конструкторе,
тоже закрывает рекомендацию при следующем анализе. Применение одной кнопкой
(`Engine.advisor`) заново читает правило, накладывает patch на текущую версию
и сохраняет через конструктор; при логике «ИЛИ» добавление условия запрещено
(оно расширило бы правило).

## 8в-бис. Прибыль, EV и рабочий портфель (`profit.py`)

Точность не равна прибыли. Для каждого наблюдения хранится коэффициент
прогноза (`odds`, из снимка линии через `profit.odds_for_observation`).
Денежные метрики считаются только по наблюдениям с коэффициентом:

- `EV = p * odds - 1`, где `p` — доля побед; `ROI = прибыль / оборот`;
- `ev_lower` — EV по нижней границе Уилсона: осторожная оценка, которая не
  даёт маленькой выборке выглядеть прибыльной;
- `stake_pct` — дробный Келли с потолком `MAX_STAKE_PCT`;
- `drawdown` — максимальная просадка кривой прибыли;
- `validation` — хронологическое разделение: обучение на старых матчах,
  проверка на последних (`MIN_VALIDATION`), правило подтверждается только при
  положительном EV lower и ROI на проверке;
- `best_odds_floor` — минимальный коэффициент, при котором правило
  становится прибыльным; из него строится условие `odds.* >= floor`.

Портфель (`rule_advisor._portfolio`) — не список всех правил. В `core`
попадают только правила с `value_ready`, положительным `ev_lower` и ROI;
суммарная экспозиция ограничена `PORTFOLIO_BUDGET_PCT = 10%`, число правил —
`MAX_PORTFOLIO = 8`. Остальные получают статусы `watch`, `fragile`,
`no_odds`, `filter` или `drop`. Для каждого правила отдаются `stake_pct`,
`stake_amount`, `expected`, `roi`, `ev`, `ev_lower`, `profit`, `drawdown`.

## 8г. Несколько видов и онлайн-режим

`analysis_service.build_report` — общая точка расчёта для телефона и сайта.
Она принимает `sports` (список), строит наблюдения по каждому виду, считает
`analyzer.analyze` с готовым списком наблюдений, объединяет неудачи, удачи,
связки и средние, добавляет `sport`/`sport_name`/`sport_short` к строкам и
возвращает `{"payload": ..., "advisor_state": ...}`.

`Engine.get_analyzer`:

- нормализует фильтр через `analysis_service.parse_options` (`sports` —
  новый формат, `sport` — совместимость со старыми клиентами);
- кэширует отчёт по ревизии истории, фильтрам и подписи правил;
- при включённом онлайн-режиме отправляет сжатый снимок через
  `online_client.analyze` и принимает `advisor_state` с сервера;
- при сетевой ошибке пишет её в `online_error` и считает локально, если
  `fallback_local` не выключен.

Сервер (`server/online_app.py`) использует тот же `build_report`, поэтому
цифры онлайн и офлайн совпадают. Подробности развёртывания — `server/README.md`.

## 8д. Калибровка встроенного ансамбля (1.19)

Для настольного тенниса `ProbabilityEnsemble.aggregate` оценивает не
«среднюю точность моделей», а вероятность конкретного исхода:

```text
raw = 0.50 * agreement + 0.30 * top_share + 0.20 * coverage
confidence = 0.5 + (raw - 0.5) * n / (n + PROB_SHRINK)
```

- `agreement` — доля голосов за верхний исход с учётом веса моделей;
- `top_share` — доля этого исхода в свежей истории с затуханием
  `RECENCY_DECAY = 0.85`;
- `coverage` — какая часть активных моделей согласна с верхним исходом;
- `PROB_SHRINK = 8.0` прижимает оценку к 50% на малой выборке;
- итог ограничен диапазоном 50–97%.

Веса моделей: `recency 1.15`, `window 1.00`, `markov1 0.85`,
`markov2 0.70`, `base_rate 0.60`, `streak 0.55`. Порог голоса —
`vote_weight_base = 0.34`; модель с более низкой Wilson-точностью не
усиливает исход.

Последовательность партии объединяет очные встречи и последние пять игр
каждого игрока, сортирует их по дате и берёт только те матчи, где нужная
партия действительно игралась. На матч остаётся не больше трёх прогнозов:
лучший исход, лучший тотал и третий рынок только при уверенности ≥ 64%.
Порог 0.56 нельзя понизить настройками — это защита от возврата шумной
линии. Мягкие пороги 1.18 мигрируют в строгие при загрузке настроек, но
пользовательские значения не перезаписываются.

## 9. Ограничения

- Мало данных → выводы статистически слабые.
- Снимок содержит только то, что было на момент прогноза; более поздние игры
  в анализ не попадают.
- Анализатор не учитывает изменение линии после отправки; для денежных
  метрик используется коэффициент, сохранённый в снимке.
- Если коэффициентов нет, ROI/EV/прибыль не выдумываются: правило остаётся
  `no_odds` и не попадает в портфель.
- `with_stats` считает все прогнозы со снимком, а `observations.total` —
  только те, у которых есть и снимок, и результат, и они прошли фильтры.
- Для настольного тенниса цель (`target`) — партия, для остальных — `match`.
- Строковые метрики (лига, последний результат) в переборе не участвуют, но
  могут быть добавлены в правило вручную.

## 10. API и UI

- Python: `api_analyzer(payload)`, `api_advisor(payload)` и
  `api_auto_rules(payload)` в `engine_api.py`; `api_online(payload)` —
  статус, проверка и настройка сайта.
- JS: `state.an`, `state.attach`, `renderAnalyzer()`, галочки видов
  (`#anSport`, `analyzerSportsEffective`), фильтры рынка/цели, кнопки
  «В конструктор», `attachAsNew` / `attachToRule`.
- Рекомендации: `renderAdvisor()`, `applyAdvisor()`, `dismissAdvisor()`
  читают `data.recommendations`; применяют через `advisor` action `apply`
  и обновляют анализ.
- Онлайн: `renderOnlineStatus()`, `toggleOnline()`, `testOnlineSettings()`,
  `testOnlineFromAnalyzer()`; Kotlin `Bridge.online(payload)`.
- Проверка правил: `renderRuleReviews()` и `applyRuleReview()` читают
  `data.rule_reviews`, показывают вердикт и применяют `patch` через
  `constructor` + `saveConstructor`; после сохранения анализ обновляется.
- Авто-правила: `loadAutoStatus()`, `renderAutoRules()`, `autoToggle()`,
  `autoRefresh()`, `autoConfigure()`, `openAutoRule()`, `bindAutoRules()`.
  Payload действия: `status`, `enable`, `disable`, `refresh`, `configure`.
- Kotlin: `Bridge.autoRules(payload)` → `api_auto_rules`.
- CSS: карточки анализа, таблицы, бейджи, окно `attachModal`, `.auto-card`,
  `.auto-rule`.
- Тесты: `tests/test_auto_rules.py` (генерация, сохранение метаданных,
  API enable/configure/disable, сохранность ручных правил).

Payload:

```json
{
  "sports": ["table_tennis", "football"],
  "kind": "all",
  "target": "",
  "min_group": 3,
  "min_lift": 10,
  "min_hits": 2,
  "limit": 0
}
```

## 11. Как расширять

1. Добавьте метрику в `constructor_engine.METRICS` и в нужные виды.
2. Убедитесь, что `candidate_variants` её подхватывает (не `string`).
3. Проверьте `_numeric_candidates` для разумных порогов.
4. Прогоните `tests/test_analyzer.py`, `tests/test_auto_rules.py`,
   `tests/test_online_server.py` и
   `tests/test_sports_metrics.py`.
5. Проверьте, что снимок статистики содержит нужные поля, а `prediction`
   содержит рынок, цель и сторону для авто-генератора.
