# ARCHITECTURE

## 1. Общая схема

```text
┌──────────────────────────────────────────────────────────────┐
│ Android WebView (assets/www)                                  │
│ index.html + style.css + app.js                              │
│ состояние в JS, экраны, фильтры, редактор правил              │
└──────────────────────────┬───────────────────────────────────┘
                           │ window.PyApp.*  (синхронно)
┌──────────────────────────▼───────────────────────────────────┐
│ MainActivity.kt → Bridge (@JavascriptInterface)               │
│ каждая функция → engine_api.api_* → JSON-строка               │
└──────────────────────────┬───────────────────────────────────┘
                           │ Chaquopy
┌──────────────────────────▼───────────────────────────────────┐
│ engine_api.py — Engine (singleton), фоновый поток, API        │
│  ├─ predictor_core.py — линия, статистика, модели, результаты │
│  ├─ constructor_engine.py — правила, метрики, шаблоны          │
│  ├─ analyzer.py — разбор истории прогнозов                    │
│  ├─ auto_rules.py — авто-генерация правил по статистике       │
│  ├─ analysis_service.py — общий отчёт по нескольким видам     │
│  ├─ rule_advisor.py — рекомендации по правилам и их жизненный │
│  │                       цикл                                  │
│  ├─ online_client.py — клиент сайта совместного анализа       │
│  └─ sports.py — справочник видов, счёт, рынки, тоталы         │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTPS
         ┌─────────────────┼──────────────────┬────────────────┐
         ▼                 ▼                  ▼                ▼
  d.betcity.by/api/v1/live/bets  betcity.by/ru/mstat/<id>  сайт анализа
  live-линия и коэффициенты      статистика матча          (server/, опция)
```

Онлайн-режим необязателен. По умолчанию отчёт анализа считается на телефоне.
Если пользователь включил «Использовать онлайн», `online_client.py` отправляет
сжатый снимок на WSGI-сайт (`server/online_app.py`), который вызывает тот же
`analysis_service.build_report`. При сетевой ошибке приложение считает локально
(`fallback_local`), поэтому офлайн-работа не ломается.

`EngineService` — foreground-сервис Android. Он держит процесс живым, пока
движок запущен, и показывает постоянное уведомление. Запуск/остановка движка
идёт через `EngineService.start/stop` и параллельно через Python API.

## 2. Слои и файлы

### Android / Kotlin

- `app/src/main/java/by/betcity/predictor/MainActivity.kt`
  - создаёт WebView, скрывает системные бары;
  - инициализирует Python (`Chaquopy`);
  - `call(name, *args)` вызывает функцию `engine_api` и всегда возвращает
    строку; при исключении возвращает `{"ok": false, "error": "..."}`;
  - `Bridge` — все `@JavascriptInterface` методы;
  - сохранение/шеринг файлов, уведомления, `keepScreenOn`.
- `EngineService.kt` — foreground-сервис и уведомления.
- `AndroidManifest.xml` — permissions (INTERNET, notifications), service.
- `app/build.gradle.kts` — Chaquopy, версия, подпись debug.

### Python

- `engine_api.py`
  - singleton `Engine` (создаётся лениво функцией `engine()`);
  - фоновый поток `_loop`: `predictor.run_cycle()` → пауза
    `poll_interval_sec`;
  - JSON-API `api_*` для Kotlin;
  - очередь линии, история, фильтры, экспорт, очистка;
  - `APP_VERSION`.
- `predictor_core.py`
  - `BotSettings` — настройки и атомарное сохранение;
  - `EventLog` + файл `events.jsonl` + `predictor.log`;
  - Betcity API/линия, парсинг статистики;
  - встроенный ансамбль шести моделей (настольный теннис);
  - generic-анализ для командных видов;
  - проверка результатов, Telegram, отчёты, CSV ставок.
- `constructor_engine.py`
  - каталог метрик для каждого вида, аргументы, операторы;
  - `Context` — нормализованный матч + статистика;
  - вычисление метрик, условий, действий;
  - авто-выбор партии/стороны;
  - шаблоны (`PRESETS`, `SPORT_PRESETS`);
  - хранение правил по видам;
  - публичное описание правил для UI.
- `analyzer.py`
  - снимок контекста в момент отправки;
  - построение наблюдений, кандидатов, групп, пар, средних;
  - JSON-safe преобразование.
- `auto_rules.py`
  - группировка наблюдений по рынку и цели;
  - выбор условий удач/неудач, инверсия и проверка на всей группе;
  - вывод действия по зашедшим прогнозам;
  - стабильные `auto_key`/`id`, метаданные точности и покрытия;
  - повторная проверка старых авто-правил без изменения ручных.
- `analysis_service.py`
  - общая точка расчёта отчёта анализа для телефона и сайта;
  - принимает `sports` (список), разбирает старый `sport` для совместимости;
  - строит наблюдения по каждому виду и один общий вызов
    `analyzer.analyze`;
  - объединяет неудачи, удачи, связки, средние и проверки правил, добавляя к
    строкам `sport`/`sport_name`/`sport_short`;
  - вызывает `rule_advisor` и возвращает `{"payload": ..., "advisor_state"}`.
- `rule_advisor.py`
  - рекомендации по конкретному правилу и условию: добавить/убрать условие,
    отключить правило, исправить уверенность действия;
  - стабильный `id` = `sha1(sport | rule_id | type | condition_key)`;
  - состояние `seen`/`applied`/`resolved`/`dismissed` передаётся словарём,
    сохраняет его вызывающая сторона;
  - перед выдачей проверяет актуальное правило, поэтому ручная правка тоже
    закрывает рекомендацию; отложенный совет скрыт 7 дней.
- `online_client.py`
  - gzip-сжатие снимка, обрезка тяжёлых полей, таймаут;
  - `ping` и `POST /api/v1/analyze` с Bearer-токеном;
  - возвращает разобранный ответ сервера или сетевую ошибку.
- `nn_core.py`
  - признаки: список метрик конструктора на вид спорта (командные виды и
    настольный теннис отдельно) + доля доступных метрик + номер партии;
  - метки: победитель, ничья, тотал, фора и «обе забьют» из финального счёта
    Betcity (`tt_sets` разбирает счёт партий настольного тенниса);
  - головы сети: `p1`, `p2`, `draw`, `over`, `handicap`, `btts`
    (у настольного тенниса — `p1`, `p2`, `over`);
  - `MLP`: два скрытых слоя, сигмоидные выходы, mini-batch SGD с импульсом
    и L2-регуляризацией (`train_batch`), ранняя остановка на лучшей эпохе по
    отложенной выборке (точность, при равенстве — меньшая потеря);
  - `Standardizer` (z-score) и `evaluate_model` — точность по каждой голове,
    общая точность, потеря и базовый уровень;
  - `split_rows` — хронологическое деление выборки по матчам: все партии
    одного матча попадают только в одну часть; `evaluate_previous` проверяет
    прежнюю модель на той же отложенной выборке для честного сравнения;
  - `tt_line` — правдоподобная линия тотала партии (18.5, если линия похожа на
    тотал матча).
- `nn_trainer.py`
  - `NeuralTrainer`: примеры по всем проверенным матчам, ожидающие результат,
    разметка, фоновая нить дообучения, прогнозы, статус, сброс;
  - настройка `neural.sports` — список видов, по которым сеть отдаёт
    прогнозы, и `neural.markets` — рынки по видам (обучение идёт по всем
    видам и всем рынкам);
  - защита от переобучения: `neural.keep_best` (новая модель принимается,
    только если не хуже прежней на той же отложенной выборке), `neural.freeze`
    (веса не меняются автоматически), пауза по плато (`PLATEAU_ROUNDS = 3`
    раунда без роста; вид обучится снова при +25% новых примеров), резервная
    копия модели и `rollback()`;
  - разметка: счёт завершённого матча из фида; если матч ушёл из линии — по
    `last_score`, который сохраняется в примере, пока матч был в линии
    (`update_pending_scores`, называемый циклом движка). Теннис требует
    4 победы в партиях, командные виды — только если матч был замечен
    завершённым. Примеры старше `MAX_PENDING_AGE_HOURS = 36` удаляются,
    счётчик `dropped` — сколько потеряно из-за линии;
  - история обучения: список записей `{at, accuracy, baseline, lift,
    samples, rejected}` по каждому виду (в модели, `HISTORY_LIMIT = 30`);
  - файлы: `nn_samples.jsonl`, `nn_pending.json`, `nn_model.json`
    (`sports` — рабочие модели, `backups` — резервные копии);
  - `merge_predictions` — слияние с правилами и ансамблем без дублей.
- `ai_assistant.py`
  - клиент OpenAI-совместимого API: один код для Gemini, DeepSeek, Groq,
    OpenRouter и своего endpoint (в настройках — base_url, модель, ключ);
  - фоновые задачи (`submit`/`job`) — интерфейс не блокируется;
  - кэш ответов (`ai_cache.json`) по хэшу запроса, дневной лимит и счётчик;
  - промпты: объяснение прогноза, черновик правила, итоги, ревью правил,
    мнение по матчу (строгий JSON);
  - `match_context` — компактное описание матча (форма, очные, коэффициенты,
    линия, прогнозы) из статистики или из снимка сохранённого прогноза.
- `sports.py`
  - 6 видов, aliases, id Betcity;
  - `BETS`, `bet_definitions`, рынки;
  - `parse_score`, `record_from_score`, `margin`, `default_total`;
  - подписи периодов.

### Web UI

- `app/src/main/assets/www/index.html` — разметка 9 экранов и модалок.
- `style.css` — тёмная тема, карточки, чипы, адаптивность, документация.
- `app.js` — состояние, вызовы моста, рендер, фильтры, редактор правил,

## 3. Жизненный цикл движка

1. Пользователь нажимает «Запустить».
2. Kotlin вызывает `api_start`, затем поднимает `EngineService`.
3. `Engine.start()`:
   - сохраняет `running = true`;
   - применяет глубокие параметры (`STREAK_MIN` и т.п.);
   - запускает daemon-поток `predictor-loop`.
4. Цикл:
   - проверяет `running`;
   - получает линию всех видов одним запросом `get_live_matches()`;
   - сразу размечает завершённые матчи (`_nn_maintenance`): обновляет
     последний счёт ожидающих примеров, переносит готовые в выборку и
     запускает дообучение. Это выполняется до раннего выхода при пустой
     линии, иначе примеры копились бы без обучения;
   - режет список предстоящих матчей лимитом `max_matches_per_sport`
     (по умолчанию 10 на вид, 0 — без ограничения; остальные ждут следующего
     цикла и не помечаются обработанными);
   - для каждого предстоящего матча:
     - проверяет, не отправлялся ли уже прогноз;
     - загружает статистику Betcity;
     - считает признаки нейросети один раз
       (`nn_core.build_features`) и сохраняет образец в обучающей выборке —
       даже если прогноза по матчу не будет;
     - выбирает режим: `constructor` / встроенный TT / generic;
     - добавляет прогнозы нейросети (если включены и модель готова);
     - при включённом ИИ проверяет выбранные виды и рынки
       (`ai.markets_for`), вызывает модель и либо добавляет её мнение к
       текущим прогнозам (`embed`), либо оставляет отдельным источником;
       при `embed` и пустом списке прогнозов запрос не выполняется;
     - отправляет сообщение в Telegram (или пишет в локальное хранилище);
     - сохраняет прогноз, снимок статистики, CSV-строку;
     - помечает матч обработанным.
5. После цикла `_refresh_all_auto_rules()` (не чаще
   `AUTO_RULES_INTERVAL = 180` секунд на вид) пересобирает авто-правила
   каждого вида, если `auto_rules.enabled`.
6. `ResultChecker` в отдельном потоке периодически проверяет завершённые матчи
   и размечает примеры нейросети:
   - один снимок линии на весь проход (`live_index()`, не чаще раза в 20 с);
   - `_remember_scores()` пишет последний счёт каждого события в
     `score_cache.json` (TTL 12 ч, до 800 записей);
   - `_check_record()` выбирает проверку: партии настольного тенниса
     (`_check_table_tennis`) или матчевые рынки (`_check_match_predictions`);
   - если матч ушёл из линии, `cached_score()` берёт последний счёт из кэша —
     только если он финальный (`score_complete`), и помечает запись
     `resolved_from_cache` / `checked_from = "cache"`;
   - мнение ИИ проверяется отдельно (`_check_ai_predictions`), даже если
     обычных прогнозов нет.
7. Фоновая нить `nn-trainer` дообучает модели нейросети (не чаще
   `TRAIN_INTERVAL = 120` секунд между сессиями обучения, принудительно — по
   кнопке «Обучить сейчас»).
8. «Остановить» ставит `running = false` и будит поток; сервис останавливается.

## 4. Поток данных прогноза

```text
live/bets JSON
  → get_live_matches(sport)
  → match {match_id, sport, team1, team2, league, date, odds, stat_link,...}
  → get_match_stats(stat_link, team1, team2, sport)
  → stats {sport, h2h_matches, recent{p1,p2}, page_total, odds...}
  → Context(match, stats)
  → evaluate (constructor) или model analysis
  → predictions [{target, label, kind, verdict, expected_side,
                  threshold, handicap, confidence_val, models_info,...}]
  → TelegramBot.mark_prediction_sent(...)
  → sent_predictions.json + analyzer sample + bets_log.csv
```

`analyzer.make_sample(match, stats)` сохраняет компактный JSON-safe снимок:
`kind: "context"`, `sport`, `page_total`, `h2h`, `recent`, `match`. Снимок
восстанавливается в `Context` при анализе, поэтому анализатор видит данные на
момент прогноза. В наблюдение также попадает полный `prediction`, чтобы
`auto_rules.py` мог восстановить рынок, цель, сторону и линию действия.

## 5. Хранение

`BASE_DIR` выбирается в `_resolve_base_dir()`:

1. `PREDICTOR_HOME` или `HOME`, если папка доступна для записи;
2. приватная `filesDir` Android через Chaquopy;
3. `~/predictor`;
4. `./predictor_data`.

Внутри `BASE_DIR` создаётся `predictor_data/`:

| Файл | Содержимое |
|---|---|
| `bot_settings.json` | настройки |
| `sent_predictions.json` | отправленные прогнозы + снимки + результаты |
| `processed_matches.json` | обработанные матчи |
| `report_state.json` | время последних отчётов |
| `bets_log.csv` | журнал ставок |
| `predictor.log` | текстовый лог |
| `events.jsonl` | события для экрана «Логи» |
| `constructor_rules.json` | правила настольного тенниса |
| `constructor_rules_<sport>.json` | правила остальных видов |
| `nn_samples.jsonl` | обучающая выборка нейросети (признаки + метки) |
| `nn_pending.json` | примеры нейросети, ждущие результата |
| `nn_model.json` | веса и статистика моделей нейросети по видам |
| `score_cache.json` | последний увиденный счёт матчей (12 ч, до 800 записей) — для проверки прогнозов, ушедших из линии |
| `advisor_state.json` | жизненный цикл рекомендаций: `seen`, `applied`, `resolved`, `dismissed` |

Все записи — атомарные: `.tmp` → `os.replace`. Настройки и правила
сериализуются с `ensure_ascii=False`, UTF-8.

## 6. Потокобезопасность

- `Engine` защищает очередь и счётчики `RLock`.
- `BotSettings` — отдельный `RLock`; `snapshot()` отдаёт глубокую копию.
- `ConstructorEngine` — `RLock` вокруг правил и статистики; правила вида
  загружаются лениво.
- `TelegramBot.sent_predictions` защищён `_lock`; анализатор копирует через
  `json.loads(json.dumps(...))`.
- `EventLog` — кольцевой буфер 2000 событий под `Lock`.
- Мост Kotlin↔JS синхронный: вызовы приходят из UI-потока WebView.

## 7. Режимы прогнозирования

`settings.algorithm_mode`:

- `builtin`:
  - `sport == table_tennis` → `_analyze_all` (ансамбль шести моделей,
    по-партийные прогнозы);
  - иначе → `_analyze_generic` (форма + H2H + линия тотала, матчевые рынки).
- `constructor`:
  - `constructor.evaluate(match, stats)` для любого вида;
  - правила сортируются по приоритету;
  - `skip` помечает матч пропущенным;
  - несколько правил могут дать несколько прогнозов.

## 8. Очередь и результаты

- `Engine.refresh_queue()` получает линию всех видов, складывает в `_queue`,
  добавляет краткие прогнозы через `_attach_predictions`.
- `get_queue(sport)` умеет фильтровать по виду; UI по умолчанию показывает все
  виды и подписывает каждый матч его видом спорта.
- `get_results(...)` собирает игры из `sent_predictions`:
  - фильтры по дате/времени, поиску, статусу, виду спорта;
  - строки прогнозов, результаты, счёт, обоснование, `checked_from`
    (`"cache"` — результат взят из кэша последнего счёта);
  - суммарная сводка (включая `ai_preds`/`ai_wins`/`ai_losses`/`from_cache`)
    и CSV;
  - «Мнение ИИ» — отдельные строки с `source: "ai"`, чтобы статистику ИИ
    можно было оценивать отдельно от правил и сети.
- `get_predictions(limit, sport)` — плоский список для статистики.

## 9. Онлайн-режим и сервер анализа

```
app.js ──> Bridge.online/analyzer ──> engine_api.api_analyzer
                                           │
                              online.enabled?
                                   │           │
                                  да          нет
                                   │           │
                         online_client ──> server/online_app.py
                                   │           │
                                   └── fallback ──> analysis_service
```

- `server/online_app.py` — WSGI-приложение без внешних зависимостей:
  `GET /` — веб-кабинет, `GET /service` — статус, `GET /api/v1/ping`,
  `POST /api/v1/analyze`, `POST /api/v1/sync`, `GET /api/v1/history/*`.
- `server/app.wsgi` — точка входа для alwaysdata; `server/cgi_adapter.py` —
  CGI-вариант для статического сайта.
- `server/history_store.py` — SQLite-хранилище: устройства, прогнозы,
  правила, события изменений, рекомендации и журнал синхронизаций.
- `server/history_ui.py` — самодостаточный HTML/CSS/JS кабинета без CDN.
- `tools/prepare_server.py` собирает `dist/server/` с копиями
  `analysis_service.py`, `analyzer.py`, `rule_advisor.py`, `auto_rules.py`,
  `constructor_engine.py`, `sports.py`, а также готовый `index.html`.
- Авторизация — заголовок `Authorization: Bearer <token>`; токен задаётся
  переменной окружения `PREDICTOR_TOKEN`. Пустой токен означает открытый
  доступ (только для локальных тестов).
- `POST /api/v1/analyze` остаётся самодостаточным: снимок приходит в запросе,
  отчёт возвращается в ответе. `advisor_state` хранится на телефоне.
- `POST /api/v1/sync` сохраняет снимок: сервер обновляет правила, пишет diff
  изменений, складывает прогнозы и результаты, пересчитывает рекомендации и
  считает эффект «до/после». Секреты из настроек не сохраняются.
- Ответы сжимаются gzip, если клиент прислал `Accept-Encoding: gzip`.

Настройки: `settings.online` = `{enabled, url, token, timeout, fallback_local,
sync_enabled, sync_interval_min, last_sync, last_sync_error,
last_sync_summary}`; `settings.device` = `{id, name}`.

## 10. Внешние зависимости

Вендорены в `app/src/main/python/`: `requests`, `bs4`, `soupsieve`,
`urllib3`, `certifi`, `charset_normalizer`, `idna`, `typing_extensions` и
другие чистые Python-пакеты. `pip` при сборке не используется. Нативные
библиотеки Python и Chaquopy приходят из Gradle/Chaquopy.

## 11. Границы ответственности

- `sports.py` не импортирует движок.
- `constructor_engine.py` использует `sports` и `analyzer` не импортирует.
- `analyzer.py` может использовать `constructor_engine` и `sports`.
- `analysis_service.py` — общий слой отчёта; не знает про файлы и Android,
  вызывает `analyzer`, `auto_rules`, `rule_advisor`, `constructor_engine`.
- `rule_advisor.py` не читает и не пишет файлы: состояние передаётся снаружи.
- `predictor_core.py` использует все три модуля.
- `engine_api.py` — единственный слой, который знает про JSON-строки, файлы
  состояния и UI; он же сохраняет `advisor_state.json` и вызывает
  `online_client`.
- `server/` использует те же модули расчёта, но не импортирует
  `engine_api.py`, `predictor_core.py` и `online_client.py`.
- UI не содержит бизнес-логики прогнозов: только отображение, фильтры и
  формирование правил.
